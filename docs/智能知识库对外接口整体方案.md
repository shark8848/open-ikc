# 企业级智能知识库 V6.5 — 对外接口整体方案

> **文档构成**：本文由两部分合并而成——
> - **第一部分「对外接口分类整理」**：按能力域、消费者、开放形态三维度，枚举面向业务系统、数字员工（Agent）、RAG 原子能力与基础设施的北向接口。
> - **第二部分「集成形态与权限分级」**：将原子能力按组合深度区分为四种集成形态，阐述每种形态的集成/使用方式与权限严格度递进。
>
> 整理依据：《企业级智能知识库V6.5规划》第七层（知识服务与智能应用层）、第八层（用户/应用/Agent层）、RAG 与知识管理章节，以及 FY2026 Q3/Q4 迭代规划（RAG 组件化、开放平台能力补齐）。
>
> 范围界定：**"对外"指智能知识库平台向北向（Northbound）暴露的接口能力**，即面向「业务应用系统」「数字员工（AI Agent）」「企业用户」及「合作伙伴」开放的能力；平台内部层级间调用不在此列。

# 第一部分　对外接口分类整理

## 1. 总体分类视角

对外接口可从三个正交维度交叉归类，后续章节按维度展开。

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| **能力域** | 知识管理 KM / RAG 检索 / 语义本体 SM / 治理运营 GOV / 平台基础 PF | 决定接口"提供什么能力" |
| **消费者** | 业务应用 / 数字员工 Agent / 企业用户 / 合作伙伴 | 决定接口"给谁用" |
| **开放形态** | REST API / MCP Server / CLI / SDK / Agent Tool / Webhook 订阅 | 决定接口"怎么调用" |

> 设计原则回顾（来自规划）：知识库定位为「知识与上下文层」，对外以 **搜索、问答、API、MCP 或 Agent 工具** 等方式提供服务（核心特征"可服务化"）；数字员工的权限与操作权限须独立管理，不得继承系统最高权限。

## 2. 面向业务应用系统的对外接口

业务系统通过标准接口将知识能力嵌入客服、办公、研发、销售、运营等系统。

| 接口 ID | 接口名称 | 能力域 | 开放形态 | 能力说明 | 治理/权限要点 |
| --- | --- | --- | --- | --- | --- |
| KM-API-01 | 知识检索 API | KM / RAG | REST API | 面向业务系统的统一知识检索，支持关键词、语义、混合检索 | 权限过滤、租户/组织隔离 |
| RG-API-01 | 问答 API（基于证据） | RAG | REST API | 给定问题返回带引用与原文定位的答案，支持多轮 | 答案与证据分离、引用完整性 |
| SM-API-01 | 实体查询 API | SM | REST API | 查询业务实体（客户/产品/供应商等）及其属性关系 | 字段/行级权限、脱敏 |
| SM-API-02 | 图谱查询 API | SM / RAG | REST API | 基于知识图谱的实体关系、多跳查询（GraphRAG） | 图谱访问权限控制 |
| SM-API-03 | 术语与本体服务 | SM | REST API | 提供术语表、分类法、本体、同义词、指标口径查询 | 本体版本管理 |
| RG-API-02 | 引用及证据服务 | RAG | REST API | 返回检索证据、来源定位、原文片段，支撑可验证回答 | 溯源、密级校验 |
| KM-API-02 | 知识订阅服务 | KM | Webhook / 消息 | 知识变更/新增时主动推送（如制度更新、图谱变化） | 订阅范围授权、密级过滤 |
| KM-UI-01 | 企业统一搜索（嵌入式） | KM | Web 组件 / API | 供业务系统嵌入的统一搜索与知识导航 | 用户身份透传 |
| KM-UI-02 | 文档对比 / 知识推荐 / 专家发现 | KM | API / Web | 文档差异对比、相关知识推荐、知识责任人发现 | 权限范围内可见性 |

## 3. 面向数字员工（AI Agent）的对外接口

数字员工是规划中重点强调的消费者。知识库为 Agent 提供"任务上下文、业务语义、规则、证据和工具说明"，并承担"操作前知识校验"与"行动依据记录"。

| 接口 ID | 接口名称 | 能力域 | 开放形态 | 能力说明 | Agent 治理要点 |
| --- | --- | --- | --- | --- | --- |
| AG-Tool-01 | 上下文组装（Context Assembly） | KM / RAG | Agent Tool / MCP | 将任务相关权威知识、实时数据、语义组装为 Agent 可消费上下文 | 独立 Agent 身份、最小权限 |
| AG-Tool-02 | 知识检索工具 | RAG | Agent Tool / MCP | Agent 调用式检索（全文/向量/混合/图谱），返回带证据片段 | 检索权限不降级 |
| AG-Tool-03 | 业务对象查询 | SM | Agent Tool / MCP | 识别并查询业务对象当前状态（订单/库存/价格等） | 实时来源优先于索引副本 |
| AG-Tool-04 | 规则查询 | GOV | Agent Tool / MCP | 查询业务规则、合规条款、约束条件 | 规则版本与适用范围 |
| AG-Tool-05 | 本体与 Schema 查询 | SM | Agent Tool / MCP | 提供概念、属性、关系、状态模型供 Agent 理解任务 | 本体版本管理 |
| AG-Tool-06 | 工具参数说明（Tool Spec） | PF | Agent Tool / MCP | 暴露业务系统工具/API 的参数约束、调用说明 | 工具权限白名单 |
| AG-Tool-07 | 操作前知识校验 | GOV | Agent Tool / MCP | Agent 执行写操作前校验规则与权限，必要时触发人工审批 | 高风险操作须审批/回滚 |
| AG-Tool-08 | 行动依据记录 | GOV | Agent Tool / MCP | 记录 Agent 行动所依据的知识、规则、证据与结果 | 全链路审计 |

> **配套流程**：Agent 任务执行流程（规划第八节）明确要求——身份与权限确认 → 制定计划 → 从知识库获取上下文和规则 → 查询实时业务状态 → 生成方案 → **执行前规则校验** → 必要时人工审批 → 调用业务系统 API → 记录证据 → 经验按治理流程沉淀。上述 8 个接口即支撑该流程的北向能力。

## 6. 对外接口的通用治理约束

所有北向接口须遵循以下跨层治理要求（规划"治理"与"设计原则"章节）：

1. **权限不降级**：接入、索引、检索、生成、Agent 调用各环节均保留并执行权限控制；返回内容不得超过用户在源系统的原有权限。
2. **租户/组织/项目隔离**：支持租户、组织部门、工作空间、文档级、字段/行级、数据密级隔离。
3. **身份区分**：用户身份与 Agent 身份独立，Agent 不得默认继承系统最高权限；工具/操作权限独立管理。
4. **证据与答案分离**：同时保存检索证据、模型答案、所用模型与提示、调用工具、最终执行结果。
5. **溯源与版本**：每个重要答案可定位到原始文件/页码/数据表/业务接口；知识带来源、责任人、版本、有效期、权威等级、审核状态。
6. **敏感处理**：敏感信息识别与脱敏；跨境及地域控制；内容安全与合规。
7. **实时性**：业务实时状态优先通过 SQL/API 获取，不依赖历史向量索引副本。
8. **审计**：检索、生成、工具调用、Agent 行动全量审计；高风险回答与操作须审核/审批/回滚机制。

## 8. 第一部分小结与建议

- **对外接口的核心载体**已从"仅 API"演进为"API + MCP + CLI + SDK + Agent Tool"五态并行，其中 **MCP 是连接数字员工（Agent）的关键开放形态**，应作为对外能力的优先封装方式。
- **数字员工侧**应优先落地 AG-Tool-01~08 八项 Agent 工具（尤其上下文组装、操作前校验、行动依据记录），以支撑"智能行动级（L5）"成熟度。
- **RAG 组件化**是 Q3 重点：PF-RAG-01/02/03 将解析、索引、检索以纯能力 Pipeline 对外开放，是后续所有上层接口（KM/RG/AG）的底座。
- **治理先行**：所有接口须内建权限、溯源、版本、审计与身份区分，避免"上传文档即可聊天"的低级形态。

# 第二部分　集成形态与权限分级

> 第一部分枚举了"有哪些对外接口"。本部分回答"如何按原子能力的组合深度，把这些接口组装成不同的集成形态，以及权限严格度如何随之递进"。核心论点：**权限严格度与"持久化状态 + 对外暴露程度"正相关**——只调一个无状态解析函数，权限只需"准入"；一旦把数据落库并对外提供检索返回内容，权限就必须端到端不降级；再叠加知识治理，则进入治理级。

---

## 9. 四种集成形态总览

| 形态 | 组合（原子能力） | 数据是否落库 | 是否对外提供检索 | 权限严格度 | 对应规划目标 |
| --- | --- | --- | --- | --- | --- |
| **形态一：纯解析** | 解析 Pipeline（PF-RAG-01） | 否（结果随调用返回） | 否 | 准入级（最轻） | 专业引擎能力开放、RAG 组件化 |
| **形态二：解析 + 索引** | 解析 + 索引 Pipeline（PF-RAG-01+02） | 是（落索引，不落 RAG 库） | 否 | 数据域级 | RAG 组件化（解析/索引 pipeline 服务） |
| **形态三：解析 + 索引 + RAG存储 + 检索** | 解析 + 索引 + RAG 存储 + 检索 Pipeline（PF-RAG-01+02+03） | 是（落 RAG 存储） | 是 | 检索级（严格） | 知识管理+rag=智能知识库 3.0 |
| **形态四：库 + 解析 + 索引 + 检索** | 知识库(KM) + 上述全栈 | 是（知识中台） | 是 | 治理级（最严格） | 从知识管理向知识中台演进 |

> 组合顺序即能力叠加顺序，后一形态**包含**前一形态的全部原子能力，并额外增加能力层与权限约束层。

## 10. 形态一：纯解析（Parse-Only）

**包含原子能力**：`PF-RAG-01 解析 Pipeline`（文件解析、OCR、版面/表格识别、音视频转写、代码解析）。

**集成方式**
- 调用形态：**SDK / REST API**（无状态函数式调用）。
- 调用方传入原始文件（或文件地址 + 解析参数），平台返回结构化解析结果（文本、版面树、表格、坐标、OCR 文本等）。
- 解析结果**不在平台落库**，随响应返回后即由调用方自行处置。

**使用方式**
- 调用方已有自己的存储与检索，只想复用我们的解析/识别引擎（如 Excel 复杂解析、MinerU、PaddleOCR VL）。
- 典型：业务系统本地解析后自己建索引；第三方工具集成。

**权限模型：准入级（Admission）**
- 只需判断"该调用方**是否允许接入/调用**解析服务"——即 API Key / 服务准入 / 配额控制。
- **不做数据归属、不做内容级权限**，因为数据不持久化、不跨租户共享、不对外暴露检索结果。
- 风险面最小：解析过程可能触发内容安全（如涉敏文件），可做基础内容安全拦截，但不涉及检索权限。

**调用方职责**：持有文件、持有解析结果、自行负责后续存储与权限。
**平台职责**：提供解析能力、保证解析质量、基础内容安全。

---

## 11. 形态二：解析 + 索引（Parse + Index）

**包含原子能力**：`PF-RAG-01` + `PF-RAG-02 索引 Pipeline`（全文索引、向量索引、元数据目录；支持 Parser-Cache 按页/范围缓存）。

**集成方式**
- 调用形态：**SDK / REST API**。
- 调用方推送文档 → 平台解析 → 构建索引（全文/向量/元数据）→ 索引数据**落索引存储**（但不进 RAG 知识库、不对外提供问答/检索 API）。
- 平台提供索引的"写"能力，检索"读"由调用方自己的上层完成（或后续升级为形态三）。

**使用方式**
- 调用方想用我们的解析+索引能力把知识变成"可检索底座"，但检索/问答层自建。
- 典型：把企业文档变成向量底座，自研 RAG 应用；或先用索引能力做内部相似度/去重。

**权限模型：数据域级（Data-Scoped）**
- 比形态一**多一层"数据归属与索引隔离"**：需控制"哪些数据可被索引、索引落到哪个租户/空间/集合（collection）"。
- 关注**写入侧**权限：接入范围、索引归属、Parser-Cache 隔离、索引存储配额。
- **仍不对外暴露检索结果**，因此暂无"查询时文档/字段级权限过滤"的强诉求，但索引本身需做租户/空间隔离，防止跨域索引互访。

**调用方职责**：定义索引空间、管理检索层、对最终对外服务提供权限。
**平台职责**：解析、建索引、索引隔离、缓存管理。

---

## 12. 形态三：解析 + 索引 + RAG 存储 + 检索（全栈 RAG 服务）

**包含原子能力**：`PF-RAG-01` + `PF-RAG-02` + `PF-RAG-03 检索 Pipeline` + RAG 存储（原始内容存储、知识图谱、向量/全文索引）。

**集成方式**
- 调用形态：**REST API / MCP / Agent Tool**（全栈对外开放）。
- 完整链路：接入 → 解析 → 索引 → **持久化入 RAG 存储** → 对外提供**检索 / 问答 / 实体 / 图谱** API 与 Agent 工具。
- 对应规划"知识管理 + rag = 智能知识库 3.0 基线"。

**使用方式**
- 直接把智能知识库当作**知识中台底座**，对外服务多个部门、业务系统与数字员工（Agent）。
- 数字员工通过 `AG-Tool-01~08`（上下文组装、知识检索、业务对象查询、操作前校验、行动依据记录等）接入（见第一部分第 3 节）。

**权限模型：检索级（Query / RBAC，严格）— 规划"权限不降级"原则的主战场**
- 因为现在**对外返回知识内容**，权限必须贯穿全链路、且**查询时不降级**：
  - 租户隔离、组织/部门隔离、项目/工作空间隔离；
  - 文档级 + 字段/行级权限；
  - **查询时动态权限过滤**（检索结果按调用方身份裁剪）；
  - 敏感信息识别与脱敏；
  - **用户身份与 Agent 身份区分**，Agent 不继承系统最高权限；
  - 检索、生成、工具调用全量审计。
- 实时数据不静态化：库存/价格/订单状态等优先走 SQL/API，而非仅依赖历史索引副本。
- 证据与答案分离：返回答案的同时返回检索证据与来源。

**调用方职责**：提供身份凭证、声明调用方身份（人/Agent）、遵守平台权限策略。
**平台职责**：端到端权限执行、溯源、审计、实时数据桥接。

---

## 13. 形态四：库 + 解析 + 索引 + 检索（知识中台 / KM + RAG）

**包含原子能力**：知识管理（KM）全栈 —— 分类法/术语表/本体、知识分级 L0-L4、版本与有效期、审核发布、责任主体、冲突处理、生命周期 —— **叠加** 形态三全栈（即复用第一部分第 2~5 节的 KM/RG/SM/GOV/PF 接口面）。

**集成方式**
- 调用形态：**REST API / MCP / Agent Tool / Webhook 订阅**（与形态三同接口面，但返回内容受治理约束）。
- 不仅用 RAG 技术栈，还纳入**知识治理层**：内容进来后经历"抽取→质量校验→专家审核→发布→监控失效"，并带本体映射、知识分级、来源与审核状态。
- 对应规划"从知识管理向知识中台演进""知识管理+rag=智能知识库 3.0"。

**使用方式**
- 企业级知识中台：对外同时服务人、业务应用、数字员工，且要求**可治理、可审计、可追责**。
- 对外返回的知识受"知识等级 + 审核状态"约束（如 L2/L3 的 AI 编译/推论须标记，未审核内容不自动升级为 L1）。

**权限模型：治理级（Governance，最严格）**
- 在形态三"检索级"基础上**再叠加治理约束**：
  - 知识分级 L0-L4 管控：不同等级知识对外可见性不同（L0 原始依据、L1 正式、L2/L3 须标注、L4 临时上下文不沉淀）；
  - 权威来源 / 审核状态约束：未审核 AI 内容不得作为正式依据对外提供；
  - 知识责任人、有效期、适用范围、冲突处理；
  - AI 生成内容标识、幻觉检测、引用完整性检查；
  - 高风险场景人工复核、Agent 工具权限与执行审批、异常终止与回滚；
  - 跨境及地域控制、数据保留与销毁。

**调用方职责**：在平台治理框架内使用，配合审核/审批流程。
**平台职责**：治理全生命周期 + 形态三全部权限 + 对外服务。

## 14. 权限严格度演进规律（核心结论）

```
形态一 纯解析       → 准入级：只问"能不能调"（API Key / 服务准入）
                          │ + 数据落索引
形态二 解析+索引     → 数据域级：控制"数据落到哪个租户/空间"
                          │ + 对外提供检索返回内容
形态三 全栈RAG       → 检索级（严格）：查询时端到端权限不降级、身份区分、审计
                          │ + 知识治理层
形态四 知识中台      → 治理级（最严格）：知识分级/审核/责任人/有效期/AI标识
```

**规律**：
1. **不落库 = 权限最轻**（形态一），因为无持久状态、无跨域共享。
2. **落索引但未对外检索 = 数据域级**（形态二），重点在写入侧隔离。
3. **一旦对外返回内容 = 必须检索级**（形态三），这是"权限不降级"原则生效的起点；规划反复强调的租户/文档/字段级、动态过滤、身份区分、审计都集中在此。
4. **叠加治理 = 治理级**（形态四），在检索级之上再加知识等级与审核约束，防止未审核 AI 内容被当作权威对外提供。

## 15. 与规划迭代的映射

| 规划迭代项 | 支撑的形态 | 说明 |
| --- | --- | --- |
| 整个 RAG 组件化（去业务属性、原子能力开放） | 形态一~四 的底座 | 解析/索引/检索 Pipeline 作为纯能力开放 |
| 解析器缓存 Parser-Cache | 形态二、三 | 按页/范围缓存解析内容，隔离于各数据域 |
| FSM 文件存储管理（去业务、SDK 化） | 形态二、三、四 | 统一存储底座，适配不同存储/安全环境 |
| 知识管理 + RAG = 智能知识库 3.0 | 形态三 → 形态四 | 松耦合集成形成基线，治理层叠加 |
| 开放平台能力补齐（MCP / CLI） | 形态三、四 的调用形态 | MCP 是连接数字员工的关键开放形态 |
| 统一认证鉴权集成 | 形态三、四 | 用户/Agent 身份区分、标准协议对接 |

## 16. 第二部分选用建议

- **只想用解析引擎** → 形态一（SDK/API，准入即可，最轻量）。
- **想建自己的检索/问答层，但用我们的解析+索引** → 形态二（数据域级隔离）。
- **要把知识库当知识中台底座对外服务人/系统/Agent** → 形态三（必须上检索级权限，否则不可企业级）。
- **要可治理、可审计、可追责的企业级知识中台** → 形态四（治理级，知识分级与审核不可省略）。

> 一句话：**组合越深、对外暴露越多，权限就必须越严格**；形态三是"权限不降级"的硬门槛，形态四是企业级验收（规划第 14 条验收标准）的终点。

# 第三部分　对外权限接口定义

> 前两部分回答了"有哪些对外接口"与"如何按形态集成"。本部分定义**权限接口（Permission Interfaces）**本身——权限并非单一开关，而是与集成形态一一对应、可逐级叠加的一组北向能力。权限严格度的递增，等价于"启用的权限接口组"的递增。所有权限接口同样遵循原子化、可组合原则，并默认"最小权限、默认拒绝、权限不降级、身份区分"。

## 17. 权限接口总体框架（与集成形态对齐）

| 权限级 | 对应集成形态 | 须启用的权限接口组 | 核心差异 |
| --- | --- | --- | --- |
| **准入级** | 形态一 纯解析 | `AUTH-*` 准入与凭证 | 仅判断"能否调用" |
| **数据域级** | 形态二 解析+索引 | `AUTH-*` + `PERM-数据域组` | 增加数据归属与索引隔离 |
| **检索级** | 形态三 全栈 RAG | 上述 + `PERM-RBAC组` | 增加查询时动态过滤、身份区分、脱敏 |
| **治理级** | 形态四 知识中台 | 上述 + `GOV-P-*` + `AUDIT-*` | 增加知识分级/审核/审批/审计 |

## 24. 权限接口设计要点与示例

**设计要点**
1. **原子化、可组合**：每个权限接口独立启用，按形态逐级叠加，不绑架业务。
2. **默认拒绝（default-deny）**：未显式授权即不可访问，契合 PERM-10。
3. **权限不降级**：权限在接入、索引、检索、生成、Agent 调用每一跳都执行，不因链路变长而丢失（核心落在 PERM-07 查询时动态过滤）。
4. **身份区分**：用户与 Agent 使用不同主体类型（PERM-05），Agent 不继承系统最高权限。
5. **证据与审计**：所有权限决策与知识访问留痕（AUDIT-*），支撑溯源与追责。

**示例 1 — 身份区分注册（PERM-05）**
```json
POST /perm/principal
{
  "principal_id": "agent-fin-007",
  "principal_type": "agent",
  "owner": "finance-team",
  "max_privilege": "read_only"
}
```

**示例 2 — 查询时动态权限过滤规则（PERM-07）**
```json
PUT /perm/policy/query-filter
{
  "scope": "collection:kb-fin",
  "enforce_at_query": true,
  "rules": [
    { "field": "secrecy_level", "allow": ["L0","L1","L2"] },
    { "doc_acl": "inherit_from_source" },
    { "field_mask": ["salary","id_card"] }
  ]
}
```

**示例 3 — 知识分级可见性（GOV-P-01）**
```json
PUT /gov/permission/level-visibility
{
  "L0": { "external": true,  "as_evidence": true },
  "L1": { "external": true,  "as_evidence": true },
  "L2": { "external": true,  "must_label": "AI编译" },
  "L3": { "external": true,  "must_label": "AI推论" },
  "L4": { "external": false, "no_persist": true }
}
```
