# 检索能力优化方案：普通检索 + 深度检索（对接 knowledge_transformer）

> 状态：方案稿（待评审）
> 日期：2026-08-17
> 范围：open-ikc 检索域（对外四类能力之「检索」）接口与实现优化
> 下游：`/home/cti-sc-ryc/knowledge_transformer`（universal_retriever + openai_search_service）

## 1. 背景与目标

当前 open-ikc 检索只有单一接口 `POST /api/v1/knowledge-search/query`，`mode=search|qa` 二选一，
检索内核为进程内关键词索引（`app/services/search_store.py`），`mode=qa` 的回答为占位生成
（`app/services/search.py::_placeholder_answer`）。

目标：

1. 将检索对外能力划分为**普通检索**（证据列表，低延迟、可重排）与**深度检索**（Agentic 多轮检索 +
   带引用回答，高延迟、面向复杂问题）两类，接口与参数按两种语义分别设计。
2. 检索后端最终对接 `knowledge_transformer` 的检索能力，open-ikc 只做协议转换、权限收敛与编排，
   不再维护进程内检索内核作为生产路径。
3. 不破坏统一协议（`errCode/errMsg/data/traceId`）、AUTHN/AUTHZ 契约、数据权限边界（§4）。

## 2. 现状与问题

| 现状 | 问题 |
| --- | --- |
| 单接口 `mode` 承载证据与问答两种差异较大的语义 | 深度检索（Agentic 多轮、记忆、引用）无法在现有 schema 内表达 |
| 进程内关键词索引（`SearchIndexStore`） | 无语义检索/重排/多路召回，qa 回答为占位，与生产检索能力脱节 |
| 无下游检索客户端与配置 | 无 `knowledge_transformer` 接入点、超时/重试/错误映射 |
| `mode=qa` 默认但回答是占位文案 | 调用方拿到假回答，存在误导风险 |
| 错误码未覆盖检索执行失败（V2 方案定义 `300001`，registry 未注册） | 下游失败只能落 `999999`，语义不精确 |

## 3. 下游能力盘点（knowledge_transformer）

### 3.1 universal_retriever（统一检索内核，默认端口 8096）

- `POST /retrieval/search/sync`：同步检索，直接返回 `RetrievalResponse`（普通检索首选入口）。
- `POST /retrieval/search` + `GET /tasks/{task_id}`：异步任务提交（长召回可选）。
- `POST /compat/ryc/search`、`/vector_search`、`/vector_search_v2`、`/hybrid`：容翼查兼容口径。
- 能力：`retrieval_mode=fulltext|vector|hybrid`；可插拔后端 ES（BM25+knn+RRF）/Milvus/pgvector/Solr；
  融合 `linear`/`rrf`；可配 `embedding`、`rerank` provider；`filters` 结构化过滤；`score_threshold` 阈值过滤；
  `related_top_k` 关联召回；响应含 `docs[].scores`（lexical/vector/rerank/final）与 `timings`/`used_config`。
- 请求核心字段：`query`、`retrieval_mode`、`index`、`top_k`、`page`、`page_size`、`filters`、
  `hybrid{strategy,text_weight,vector_weight}`、`vector_model_params`、`rerank_model_params`、
  `related_top_k`、`request_id`。

### 3.2 openai_search_service（检索服务网关，默认端口 8088，前缀 `/km/search-api/aiTools/openai/bsapi`）

| 接口 | 语义 | 与 open-ikc 能力的对应 |
| --- | --- | --- |
| `POST /VectorSearchV2` / `VectorSearchV3` | 基础检索（全文/向量/混合、多向量通道、查询优化、重排、降级），返回 `DocIndexItem[]` 证据 | **普通检索**（可选网关入口） |
| `POST /UniversalSearch` | 与 VectorSearchV2 同一执行路径，历史兼容 | 普通检索（别名） |
| `POST /DeepSearch` | Agentic DeepSearch（LangGraph）：记忆注入 → 图像理解 → 查询改写 → 子查询规划 → 并行多轮检索 → 反思 → 回答 → 记忆更新；受 `OPENAI_SEARCH_ENABLE_DEEPSEARCH` 开关控制（关闭时 403） | **深度检索** |
| `GET /healthz` | 健康检查 | 启动探测 |

- 请求公共字段（`MultiModalRagSearchRequest`）：`user_id`、`org_id`、`search_id`、`ct_id`（逗号分隔知识库 ID）、
  `index`、`query{text,images}`、`searchType`（0 全文 / 1 向量 / 2 混合）、`topn`、`relNum`、`useRerank`、
  `score`、`filters`、`models{llm,mllm,embedding,rerank}`、`responseSpec`。
- `DeepSearchRequest` 增量字段：`session_id`、`memory{mode,items,keys}`、
  `deepSearch{enabled,mode,maxSteps,allowOverrideSearchType,recallTopnPolicy,stopWhen,subQuery,react}`。
- `DeepSearchResponse`：`result{answer,used_queries}`、`citations[]`、`data[]`（召回明细）、`extra`。

### 3.3 服务关系

`openai_search_service` 检索主路径进程内调用 `universal_retriever` 内核；`universal_retriever_pipeline`
为可选 stage 编排入口（当前不作为 open-ikc 直接依赖）。open-ikc 建议**普通检索直连
`universal_retriever /retrieval/search/sync`**（少一跳、字段更薄），**深度检索直连
`openai_search_service /DeepSearch`**；如部署侧希望统一走网关，普通检索也可切 `VectorSearchV2`
（通过 `OPEN_PLATFORM_SEARCH_BACKEND` 切换，见 §6.3）。

## 4. 总体设计

### 4.1 接口形态（推荐：独立双接口）

| 接口 | 路径 | 语义 | 对应下游 |
| --- | --- | --- | --- |
| 普通检索 | `POST /api/v1/knowledge-search/query`（保留，兼容现有调用方） | 返回证据列表，可选重排/关联召回；`mode=search` 仅证据，`mode=qa` 附简短回答（见 §5.1 回答策略） | `universal_retriever /retrieval/search/sync`（可切 `VectorSearchV2`） |
| 深度检索 | `POST /api/v1/knowledge-search/deep-query`（新增） | Agentic 多轮检索 + 带引用回答 + 子查询/步骤明细 | `openai_search_service /DeepSearch` |

选型理由：

- 两种语义的请求参数、延迟预算、超时与错误处理差异大（普通秒级、深度十秒级），独立接口便于分级
  超时/限流/审计。
- 保留 `/query` 路径避免破坏现有调用方与测试（`tests/test_search.py`、token 作用域测试等）。
- 深度检索作为「第五类」之外检索域内的子能力，不违反 AGENTS.md §1 能力面约束。

### 4.2 能力映射

| open-ikc 语义 | 下游映射 |
| --- | --- |
| `searchType=fulltext/vector/hybrid` | `retrieval_mode=fulltext/vector/hybrid`；走 OpenAI 网关时 `searchType=0/1/2` |
| `kbId/kbIds` | `ct_id`（逗号拼接，仅传授权通过的 kb_id）；`index` 按映射表或 collocation 解析 |
| `topK` | `top_k` / `topn`（上限 100，下游 200 内） |
| `filters` | 透传结构化过滤（下游已支持 bool.filter 形态） |
| `useRerank` | `rerank_model_params`（默认 rule 重排兜底）/ `useRerank=1` |
| `score` | `score_threshold` / `score` 阈值 |
| `relNum` | `related_top_k` / `relNum` 关联召回 |
| `withCitation` | 控制 open-ikc 响应中 `citation` 字段是否填充 |
| traceId | 透传 `request_id`（UR）与 `X-Trace-Id`/`X-Request-Id`（OpenAI Search） |
| 身份 `user_id/tenant_id` | `user_id`/`org_id`（由 open-ikc 从 identity 注入，下游不做鉴权信任） |

### 4.3 分层（保持 AGENTS.md §2 分层规则）

```text
routers/search.py         薄路由：校验入参 → authorize_or_raise（逐 kb）→ SearchService
services/search.py        业务编排：权限校验 + 数据范围收敛 → 下游客户端 → 响应组装
services/search_client.py 下游适配：UniversalRetrieverClient / OpenAISearchClient（httpx，超时/重试/错误映射）
knowledge_transformer     universal_retriever / openai_search_service（外部服务，不依赖其源码）
```

- 下游只接收**已通过授权**的 `kb_id` 集合，权限与数据范围收敛全部在 open-ikc 完成，禁止把
  调用方身份透传给下游做鉴权（下游为内网可信组件）。
- `app/services/search_store.py`（进程内索引）保留为 `in_process` 占位后端，仅离线/测试用。

## 5. 接口定义

### 5.1 普通检索 `POST /api/v1/knowledge-search/query`

沿用现有 `SearchQueryRequest`，新增可选字段（全部可选，缺省走服务端默认）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `query` | string | 必填 | 检索问题/关键词 |
| `kbId` / `kbIds` | string / array | 必填其一 | 目标知识库（权限资源） |
| `teamId` / `orgId` / `ownerId` / `orgPath` | string | "" | 权限上下文（保持现状） |
| `mode` | string | `qa` | `search` 仅证据；`qa` 附简短回答（回答策略见下） |
| `searchType` | string | `hybrid` | `fulltext`/`vector`/`hybrid` |
| `topK` | int | 5 | 1~100 |
| `relNum` | int | 0 | 0~200 关联召回数量 |
| `useRerank` | bool | false | 是否重排 |
| `score` | float | 可选 | 分数阈值 |
| `filters` | object | {} | 元数据过滤（透传下游） |
| `withCitation` | bool | true | 是否返回引用信息 |
| `index` | string | 可选 | 目标索引名（缺省由 kb 映射解析） |
| `isOptimize` | bool | false | 是否开启查询优化（走 OpenAI 网关时对应 `is_optimize`） |

回答策略（`mode=qa`）：

- 阶段一：`mode=qa` 返回证据 + `answer` 为下游返回的简短回答（UR 无回答能力时返回空串，
  并在 `data.qaNote` 提示使用深度检索），**不再返回占位文案**。
- 阶段二（可选）：接入 open-ikc 侧配置的 LLM（`OPEN_PLATFORM_SEARCH_QA_LLM_*`）基于证据生成简答。

响应（`SearchQueryData`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `answer` | string | `mode=qa` 时的简短回答（可为空） |
| `total` | int | 证据总数 |
| `results[]` | array | `docId`/`docTitle`/`score`/`snippet`/`citation`/`metadata`（可选） |
| `searchType` | string | 实际执行的检索类型 |
| `usedConfig` | object | 可选，下游 `used_config` 摘要（索引、阈值、重排） |

### 5.2 深度检索 `POST /api/v1/knowledge-search/deep-query`

请求（`DeepSearchQueryRequest`）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `query` | string | 必填 | 复杂问题 |
| `kbId` / `kbIds` | string / array | 必填其一 | 目标知识库（权限资源） |
| `teamId` / `orgId` / `ownerId` / `orgPath` | string | "" | 权限上下文（保持现状） |
| `searchType` | string | `hybrid` | `fulltext`/`vector`/`hybrid` |
| `topK` | int | 8 | 每轮召回窗口（1~100） |
| `useRerank` | bool | true | 深度检索默认重排 |
| `sessionId` | string | 可选 | 会话 ID（服务端记忆） |
| `memory` | object | 可选 | `{mode: caller, items: [...]}` 调用方注入记忆 |
| `deepSearch` | object | 服务端默认 | `maxSteps`（默认 5）、`subQuery{enabled,maxSubQueries,mergeStrategy}`、`stopWhen{minEvidence,minFinalScore,maxLatencyMs}`、`recallTopnPolicy`（`fixed`/`adaptive`） |
| `filters` | object | {} | 元数据过滤（透传） |
| `responseSpec` | object | 可选 | `{include: ["answer","citations","steps"]}` |

响应（`DeepSearchQueryData`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `answer` | string | 最终回答（带证据编号引用） |
| `total` | int | 召回证据总数 |
| `results[]` | array | 召回明细（`docId`/`docTitle`/`score`/`snippet`/`citation`） |
| `citations[]` | array | 回答引用（`docId`/`docTitle`/`score`/`snippet`/`position`） |
| `usedQueries[]` | array | 实际执行的子查询列表 |
| `steps[]` | array | 可选，agent 步骤（`stage`/`query`/`docsCount`/`elapsedMs`） |

### 5.3 样例

普通检索：

```json
{
  "query": "2026 产品白皮书的核心能力是什么？",
  "kbId": "kb_10001",
  "searchType": "hybrid",
  "topK": 5,
  "useRerank": true,
  "mode": "search"
}
```

深度检索：

```json
{
  "query": "对比 2025 与 2026 产品白皮书的检索能力差异，并给出结论",
  "kbIds": ["kb_10001", "kb_10002"],
  "searchType": "hybrid",
  "deepSearch": { "maxSteps": 5, "subQuery": { "enabled": true, "maxSubQueries": 3 } }
}
```

## 6. 服务层设计

### 6.1 SearchService

- `SearchService.query(payload, owner_id, tenant_id)`：保留现有知识库存在性 + 个人/团队/企业范围校验，
  逐 kb 校验后调用下游；`in_process` 后端时沿用 `SearchIndexStore`（测试/离线）。
- `SearchService.deep_query(payload, owner_id, tenant_id)`：同样的权限收敛流程；下游未配置或
  DeepSearch 未启用时抛 `501001`，禁止静默降级为普通检索。

### 6.2 下游客户端（新增 `app/services/search_client.py`）

- `UniversalRetrieverClient.search_sync(...)`：`POST {UR_BASE_URL}/retrieval/search/sync`，
  响应 `RetrievalResponse` → 映射 `SearchQueryData`（`scores.final_score` → `score`，`content` → `snippet`）。
- `OpenAISearchClient.vector_search(...)` / `deep_search(...)`：`POST {OPENAI_BASE_URL}/VectorSearchV2`
  与 `/DeepSearch`，映射 `DocIndexItem[]` / `DeepSearchResponse`。
- 统一超时/重试：连接超时 + 读超时（普通 10s / 深度 60s，可配）；仅对连接类错误重试 1 次（幂等检索）。
- 日志：走 `log_center_sdk.get_logger(__name__)`，记录下游 `route`/`elapsed_ms`/`result_count`/`traceId`，
  不记录 token 与密钥。

### 6.3 配置与开关（环境变量）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `OPEN_PLATFORM_SEARCH_BACKEND` | `in_process` | `in_process`（占位/测试）/ `ur`（普通检索走 universal_retriever）/ `openai`（普通+深度均走 openai_search_service） |
| `OPEN_PLATFORM_UR_BASE_URL` | `http://127.0.0.1:8096` | universal_retriever 地址 |
| `OPEN_PLATFORM_OPENAI_SEARCH_BASE_URL` | `http://127.0.0.1:8088/km/search-api/aiTools/openai/bsapi` | openai_search_service 地址 |
| `OPEN_PLATFORM_OPENAI_SEARCH_TOKEN` | 可选 | 下游 Bearer（若下游启用鉴权） |
| `OPEN_PLATFORM_SEARCH_TIMEOUT_SECONDS` | `10` | 普通检索超时 |
| `OPEN_PLATFORM_DEEP_SEARCH_TIMEOUT_SECONDS` | `60` | 深度检索超时 |
| `OPEN_PLATFORM_KB_INDEX_MAP` | 可选 JSON | kb_id → index 映射，如 `{"kb_10001":"kb_chunks_write"}`；缺省交由下游 collocation 解析 |

- `ur`/`openai` 后端下，深度检索仅在配置了 `openai` 后端且下游 DeepSearch 可用时开放；否则 `/deep-query` 返回 `501001`。
- 启动脚本 `scripts/start_open_platform.sh` 增加上述变量默认导出，README 补充说明。

### 6.4 错误映射

| 场景 | 错误码 | 处理 |
| --- | --- | --- |
| 下游超时 / 连接失败 | `300001`（新增注册，见 §7） | `SearchException(SearchErrorCodes.SEARCH_FAILED, {"reason": ...})` |
| 下游返回非成功 errCode | `300001` | 透传下游 errMsg |
| DeepSearch 未启用（下游 403） | `501001` | 提示深度检索未启用 |
| 后端未配置（`in_process` 下请求 `/deep-query`） | `501001` | 提示需配置下游 |
| 参数校验 | `100001` | 沿用全局处理器 |

### 6.5 Trace 透传

- 普通检索：`request_id=traceId` 传入 `RetrievalRequest`，请求头透传 `X-Trace-Id`/`X-Request-Id`。
- 深度检索：`search_id=traceId`，`session_id` 独立透传。
- 复用 `app/core/trace.py::build_trace_headers()`，保持日志中心跨链路聚合。
