# 开放平台检索接口重设计方案（基于历史检索接口定义盘点）

> 状态：设计草案（待评审后落码）
> 依据：`docs/_excel_interfaces_extracted.json` 检索相关接口定义 + `docs/开放平台接口详细定义_精简版_V2.md` D-01 + 当前实现 `app/schemas/search.py` / `app/services/search.py`
> 原则：不扩大能力面（检索仍属四类业务能力内）、向后兼容、权限不降级、能力分级开放

## 1. 背景

开放平台当前检索接口（D-01 `POST /api/v1/knowledge-search/query`）为占位实现：关键词进程内匹配、`qa` 回答占位生成。历史系统（小思知识库平台）已具备成熟的检索工作流能力，盘点 `_excel_interfaces_extracted.json` 后，可将其中**对外可复用**的检索能力按开放平台协议重新设计，避免能力断层，同时保持统一响应体与数据权限语义。

## 2. 历史检索接口能力盘点（Excel 抽取）

| 历史接口 | 类别 | 关键能力 | 开放平台映射 |
| --- | --- | --- | --- |
| `/km/search-api/aiTools/VectorSearchV2` | 内部搜索工作流 | 关键词召回、搜索方式、topn、关联召回、分区、向量/重排模型、分数阈值、问题优化、folderLabel | 检索参数模型（部分收敛开放） |
| `/km/search-api/aiTools/openai/bsapi/VectorSearchV2` | 第三方开放搜索 | **图文检索**（images/imageStrategy/combine）、结构化 filters、模型配置集合 models{llm/mllm/embedding/rerank} | 新增图文检索与过滤能力 |
| `/km/search-api/aiTools/openai/DeepSearch` | 第三方开放深度检索 | 多轮 Agent 编排（optimize_query→retrieve→rerank→answer）、agent_steps 轨迹、image_understanding、memory_used、debug（timing/retrieval/rerank/model_calls）、include 控制字段 | 后续阶段（编排型检索），先定义出参骨架 |
| `/km/search-api/aiTools/aiKlgSearchTest/searchTest` | 搜索测试工作流 | 溯源文件（isPegFile）、rerank_weight、mixMode、高级召回参数 | 内部测试能力，不对外 |
| `/km/sagentPlatform/aiKlg/queryChunk` | 知识分段查询 | 按知识库/分段分页查询 chunk | 与文档/解析域关联，作为检索结果溯源定位的辅助信息 |
| `/km/sagentPlatform/aiKlg/queryAiKlgDatasetList` | 知识库列表 | 分页、来源类型、权限类型、组织/项目过滤 | 已由知识库域 `/knowledge-bases/query` 承接 |

结论：对第三方开放接口的核心差异点集中在 **图文检索、重排/分数阈值、问题优化、结构化过滤、可选调试信息**；深度检索（DeepSearch）可作为后续阶段以 `include` 控制字段渐进开放。

## 3. 现状与差距分析

| 维度 | 现状（D-01） | 历史能力 | 差距 |
| --- | --- | --- | --- |
| 检索方式 | 关键词进程内匹配 | keyword/semantic/hybrid + 分区 | 缺 searchType、partitions 语义 |
| 图文检索 | 不支持 | images + imageStrategy + combine | 缺 |
| 相关性控制 | 无 | score 阈值、useRerank、relNum、maxToken | 缺 |
| 问题优化 | 无 | is_optimize + 模型 | 缺（可收敛为布尔开关） |
| 过滤 | filters 元数据 | filters 结构化过滤 | 一致，语义待对齐 |
| 结果溯源 | citation（页码/位置） | docid/attachId/页码/父路径 | 缺 chunkId/attachId/定位信息 |
| 回答 | 占位生成 | LLM 证据作答 | 占位（接真实引擎替换） |
| 调试/可观测 | 无 | debug/agent_steps（DeepSearch） | 缺（include 控制可选返回） |
| 错误码 | 复用通用码 | 检索失败等业务码 | 缺检索域业务错误码 |

## 4. 重设计目标与原则

1. **向后兼容**：现有请求字段（`query/kbId/kbIds/mode/topK/filters/withCitation/teamId/orgId/ownerId/orgPath`）全部保留、语义不变；新增字段全部可选。
2. **能力分级**：基础检索（现 D-01）→ 增强检索（score/rerank/问题优化/图文）→ 编排检索（DeepSearch 类，后续）逐步开放，避免一步到位失控。
3. **权限不降级**：检索范围仍按 `kbIds` + 知识库类型收敛；个人库仅创建者可检索；team/enterprise 依赖 AUTHZ（`owner_id`/`org_path`）。
4. **统一协议**：响应体 `{traceId, errCode, errMsg, data}`；错误码入 registry；鉴权 Bearer + trace 头不变。
5. **模型不透明**：调用方不直接指定模型 ID（历史 `models` 集合默认不开放），由库级默认配置承载；确需开放列为评审决策点。

## 5. 重设计接口定义

### 5.1 请求模型（增强版 `SearchQueryRequest`）

接口名：`universalRetriever`（统一检索器）；路径：`POST /api/v1/knowledge-search/universalRetriever`（统一 POST，承载复杂检索条件）。

| 字段 | 类型 | 必填 | 默认 | 说明 | 来源 |
| --- | --- | --- | --- | --- | --- |
| query | string | 否* | "" | 检索问题/关键词（与 images 至少其一） | 保留 |
| kbId | string | 否 | "" | 目标知识库 ID（与 kbIds 至少其一） | 保留 |
| kbIds | array<string> | 否 | [] | 多库联合检索 | 保留 |
| teamId / orgId / ownerId / orgPath | string | 否 | "" | 数据权限上下文 | 保留 |
| mode | enum | 否 | qa | search / qa | 保留 |
| topK | integer | 否 | 5 | 召回证据数量上限（1–100） | 保留 |
| filters | object | 否 | {} | 元数据结构化过滤 | 保留，对齐历史 filters |
| withCitation | boolean | 否 | true | 是否返回引用/溯源 | 保留 |
| searchType | enum | 否 | hybrid | keyword / semantic / hybrid | 新增（映射历史 searchType） |
| score | number | 否 | 无 | 相关性分数阈值，低于则过滤 | 新增（映射历史 score） |
| useRerank | boolean | 否 | false | 是否启用重排 | 新增（映射历史 useRerank） |
| isOptimize | boolean | 否 | false | 是否对 query 做问题优化 | 新增（映射历史 is_optimize） |
| partitions | array<string> | 否 | [] | 搜索分区限定 | 新增（映射历史 partitions） |
| relNum | integer | 否 | 0 | 关联召回数量 | 新增（映射历史 relNum） |
| maxToken | integer | 否 | 无 | 召回内容 token 上限 | 新增（映射历史 maxToken） |
| images | array<object> | 否 | [] | 图文检索图片：`{id, url/base64 二选一, mime, hint}` | 新增（映射 openai VectorSearchV2） |
| imageStrategy | enum | 否 | ocr_caption | ocr_only / caption_only / ocr_caption | 新增 |
| combine | enum | 否 | concat | 图文融合方式：concat 等 | 新增 |
| include | array<enum> | 否 | [] | 可选返回：`usage` / `debug` / `image_understanding` | 新增（映射 DeepSearch include） |

校验约束：
- `query` 与 `images` 至少提供一个非空；`kbId`/`kbIds` 至少提供一个。
- `searchType`/`imageStrategy`/`combine` 枚举校验；`topK`/`relNum`/`maxToken`/`score` 范围校验（非负、上限 100）。
- `images[].url` 与 `images[].base64` 二选一，其余字段可选。

### 5.2 响应模型（增强版）

| 字段 | 类型 | 说明 | 来源 |
| --- | --- | --- | --- |
| traceId / errCode / errMsg | string | 统一协议 | 保留 |
| data.answer | string | qa 模式回答（当前占位生成，接真实引擎替换） | 保留 |
| data.total | integer | 命中证据总数 | 保留 |
| data.results[] | array | 检索结果列表 | 保留 |
| data.results[].docId | string | 文档 ID | 保留 |
| data.results[].docTitle | string | 文档标题 | 保留 |
| data.results[].score | number | 相关性分值 | 保留 |
| data.results[].snippet | string | 命中片段 | 保留 |
| data.results[].citation | object | 引用信息（page/position） | 保留 |
| data.results[].chunkId | string | 命中分段 ID（溯源定位） | 新增（映射历史 zj_id/docid） |
| data.results[].attachId | string | 附件/文件 ID（溯源下载） | 新增（映射历史 attachId） |
| data.results[].kbId | string | 所属知识库 ID | 新增 |
| data.results[].metadata | object | 命中文档元数据 | 新增 |
| data.usage | object | 调用统计：`{inputTokens, outputTokens, totalTokens}`（include=usage 时返回） | 新增 |
| data.debug | object | 调试信息（include=debug 时返回，脱敏）：`timing_ms`、`retrieval`、`rerank`、`model_calls` | 新增（映射 DeepSearch debug） |
| data.imageUnderstanding | object | 图文理解中间结果（include=image_understanding 时返回，逐图） | 新增 |

### 5.3 错误码（新增检索域业务码，入 registry）

| 错误码 | 消息 | 说明 |
| --- | --- | --- |
| 300001 | 检索执行失败 | 检索链路（召回/重排/问答）执行异常（对齐 V2 方案） |
| 300002 | 检索参数不合法 | 检索参数校验失败（亦可复用 100001，二选一，见决策点） |
| 300003 | 目标知识库不可检索 | 知识库不存在/未授权/无索引 |

通用码沿用：`100001` 参数错误、`100401` 未认证、`100403` 无权限、`100404` 资源不存在、`999999` 系统错误。

### 5.4 鉴权与数据权限（保持不变）

- 认证：`Authorization: Bearer <token>`（缺失/错误 `100401`）。
- 数据权限：`kbIds` 逐库校验——个人库仅创建者可检索（越权 `100403`）；team/enterprise 由 AUTHZ 策略收敛（`owner_id`/`org_path`），AUTHZ 关闭时仅校验存在性与个人库归属。
- 检索执行必须位于调用方可访问的知识库可见范围内，禁止跨库越权。

### 5.5 兼容性

- 全部现有请求字段语义不变；新增字段缺省时行为与现状完全一致（`searchType=hybrid` 等价于现关键词匹配+后续语义召回接入）。
- 响应新增字段仅在对应能力启用/`include` 指定时返回，不破坏现有消费方解析。
- **路径变更**：`/knowledge-search/query` → `/knowledge-search/universalRetriever`（Breaking Change）；旧路径是否保留为兼容别名见决策点 6。
- 除路径外，现有请求字段语义不变；新增字段缺省时行为与现状一致。
- 响应新增字段仅在对应能力启用/`include` 指定时返回，不破坏现有消费方解析。

### 5.6 请求示例（增强检索）

```json
{
  "query": "2026 产品白皮书的核心能力是什么？",
  "kbId": "kb_10001",
  "mode": "qa",
  "topK": 5,
  "searchType": "hybrid",
  "score": 0.6,
  "useRerank": true,
  "isOptimize": true,
  "filters": {"docType": "whitepaper"},
  "include": ["usage"]
}
```

图文检索示例：

```json
{
  "query": "请根据图片识别产品型号并检索相关参数",
  "kbIds": ["kb_10002"],
  "images": [
    {"id": "img1", "url": "https://oss.example.com/p.png", "mime": "image/png", "hint": "产品铭牌"}
  ],
  "imageStrategy": "ocr_caption",
  "combine": "concat",
  "mode": "search",
  "topK": 10
}
```

## 6. 分期落地建议

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| Phase 0（现状） | 关键词进程内检索 + 占位 qa | 已上线 |
| Phase 1 | 请求/响应模型升级（searchType/score/useRerank/isOptimize/partitions/relNum/maxToken/usage），枚举与范围校验，错误码 300001 入 registry，结果补 chunkId/attachId/kbId/metadata | 本次评审通过即可落码 |
| Phase 2 | 图文检索（images/imageStrategy/combine）与 imageUnderstanding 返回；接真实召回引擎替换关键词匹配 | 检索/OCR 引擎就绪 |
| Phase 3 | DeepSearch 编排型检索（agent_steps/debug/include）按场景灰度开放 | 问答引擎就绪 |

## 7. 评审决策点（需确认）

1. **模型配置是否开放**：历史 `models{llm/mllm/embedding/rerank}` 是否允许调用方指定？建议默认不开放（走库默认），仅开放 `useRerank`/`score` 等行为开关。
2. **错误码粒度**：新增 `300001/300002/300003` 是否落位，还是统一复用 `100001/999999`？（建议落位 300001，与 V2 方案一致）
3. **图文检索范围**：Phase 2 是否纳入，还是仅保留结构（images 字段校验通过但引擎未接时返回 `501001`）？
4. **debug 暴露边界**：`include=debug` 返回的模型调用摘要是否脱敏后开放（建议脱敏开放，仅计时与状态，不含请求内容）。
5. **searchType 默认值**：默认 `hybrid` 还是保持现有关键词语义（`keyword`）？建议 `hybrid`（关键词+语义融合，接引擎前等价关键词）。
6. **路径兼容**：新接口名 `universalRetriever` 落地后，旧路径 `/knowledge-search/query` 是否保留为兼容别名（建议保留至 1.1 再废弃，避免破坏存量调用方）。
