# 解析能力场景分析：需库（知识→解析→检索）与免库纯解析

> 日期：2026-08-18 · 状态：已评审，免库独立解析接口已落地（见 §3）
> 结论先行：**场景 A（需库）当前接口完全满足；场景 B（免库纯解析）不满足**——现状强制「先建库再解析」。本次新增 `POST /api/v1/knowledge-documents/parse-direct` 独立解析接口补齐场景 B，不改变场景 A 的既有协议与权限模型。

## 1. 两种场景定义

| 场景 | 业务诉求 | 需要的能力 | 典型调用方 |
| --- | --- | --- | --- |
| **A. 知识库全链路** | 建库管理知识空间 → 入库 → 解析 → 检索问答 | 知识库 + 文档 + 解析 + 检索 | 企业知识中台、RAG 应用、客服问答 |
| **B. 免库纯解析** | 只把文件/URL 解析为结构化文本（JSON/Markdown），不需要知识空间、不参与检索 | 仅解析 | 文档处理工具、数据抽取流水线、一次性转换任务 |

## 2. 现状接口与满足度分析

| 环节 | 场景 A | 场景 B（免库） |
| --- | --- | --- |
| 创建知识库 | ✅ `POST /knowledge-bases/create` | ❌ 为解析而被迫建库 |
| 接入文档 | ✅ `POST /knowledge-documents/ingest`（kbId 必填） | ❌ `ingest.kbId` 为必填字段 |
| 启动解析 | ✅ `POST /knowledge-documents/parse`（kbId+docId） | ❌ `parse.kbId`/`docId` 均必填，且 doc 必须已登记 |
| 查询/凭证/下载 | ✅ `parse-result/query`、`issue-download-ticket`、`download` | ❌ 均以 docId 定位，docId 必须来自知识库文档 |
| 检索 | ✅ `universal-search` / `deep-search` | 不适用（无库可检） |

**结论：场景 B 目前必须走「建库 → 入库 → 解析 →（清理库）」路径**，存在三方面问题：

1. **语义错配**：解析本身不需要知识空间归属，却强制要求 `kbType`（personal/team/enterprise）与 `teamId`/`orgId` 等知识库建模语义，调用方需理解知识库模型才能用解析能力。
2. **数据污染**：纯解析任务产生与业务无关的库/文档记录，污染知识空间，事后还需调用方自行清理。
3. **上手成本**：最短路径也要 3 次请求（建库→入库→解析），且每次都要带知识库上下文。

## 3. 优化：新增免库独立解析接口

### 3.1 接口形态

```
POST /api/v1/knowledge-documents/parse-direct
```

- **语义**：对一次性传入的来源（url / file / directory / archive）直接解析；**不创建知识库、不登记文档**。
- **入参**：`reqId`、`source`（同 ingest 的 `DocumentSource`）、`parseStrategy`、`resultFormat`、`executeMode`（sync/async）、`parseMode`、`chunkStrategy`、`chunkSize`。
- **出参**：`{taskId, docId（平台生成的临时标识 pdoc_xxx，仅用于后续轮询/下载）, taskStatus, executeMode, resultInline}`。
- **后续环节**：复用现有 `parse-result/query`、`issue-download-ticket`、`download`，以返回的 `docId` 操作；`executeMode=sync` 时请求内直接返回内联结果。

### 3.2 协议与权限边界

- 属于**解析**能力域，不新增第五类业务能力，不进入 `catalog` 之外的新域。
- **不进知识库可见范围**：无 `kbId`、不参与检索索引、不产生库/文档记录。
- **数据权限**：任务归属调用方认证身份（`owner_id`/`tenant_id` 取 `request.state.identity`），查询/凭证/下载仅创建者本人可操作（与个人库语义一致的 owner 收敛）；AUTHZ 走 `resource_type="parse"`。
- **占位实现**：与现有 `parse` 一致，sync 返回模拟内联结果、async 返回任务后轮询；真实解析引擎落地后替换内容，接口形状不变。

### 3.3 收益

- 场景 B 调用链从「建库→入库→解析→清理」收敛为 **1 次请求**；
- 知识空间不再被纯解析任务污染；
- 场景 A 协议与权限模型完全不变。

## 4. 后续可优化项（非本次落地）

1. **先解析后入库**：如出现「先看解析效果再决定是否入库」的诉求，可为 `parse-direct` 增加可选 `targetKbId`，解析成功后把结果登记进知识库，一次请求打通两场景。
2. **结果生命周期**：真实解析结果文件流落地后，需为免库任务补充结果保留期（TTL）与清理约定。
3. **批量解析**：场景 B 若出现批量转换诉求，可基于 `parse-direct` 增加批量任务接口（当前目录/压缩包 source 已可承载单次批量）。
4. **SDK / MCP / CLI 覆盖**：`parse-direct` 当前仅 REST 落地；Python/Java SDK、MCP 工具与 CLI 子命令的同步支持可作为后续迭代（新增工具/命令时同步 `docs/MCP与CLI接口定义.md`）。
